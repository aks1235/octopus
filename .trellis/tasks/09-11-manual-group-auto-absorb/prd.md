# 手动分组自动吸纳新渠道模型

## Goal

恢复 v1 的「渠道有新增 → 分组自动更新」体验,落在 v2 的分组模型上:**手动分组(member_regex 为空)在渠道新增/更新后,自动把该渠道下模型名匹配分组名的授权吸纳为成员**。正则分组行为完全不变。

## Background

- v1:渠道侧 `auto_group` 字段(默认正则匹配),渠道增/改时 `ChannelAutoGroup` 把渠道模型批量 upsert 进所有匹配分组(只增不减);启动时 `ChannelAutoGroupAll` 兜底。
- v2(ADR-0002):自动成员改为分组侧 `member_regex`,渠道增删改 + 5 分钟定时兜底自动重算(整体替换)。手动分组只剩编辑器内一次性「自动添加」按钮(前端动作,规则不留存,`web/src/components/modules/group/Editor.tsx:489`)。
- 用户诉求:默认(手动)分组也要自动更新,不想每次加渠道后挨个点按钮。

## Requirements

- R1 触发时机:渠道**新增**、渠道**更新**(含加 Key、模型列表变化等一切走 `ChannelCreate`/`ChannelUpdate` 的路径)后,对全部手动分组执行吸纳。`ChannelEnabled`/`ChannelDel` 不产生新授权,不挂。
- R1b 分组侧触发(UI 验证发现,2026-09-11 补):手动分组**创建时**(member_regex 为空)立即对该分组吸纳存量匹配授权——与正则分组创建即吸纳对称;手动分组**改名时**同样立即按新名吸纳。仅保存成员/删成员(未改名)不触发,避免一保存就把刚删的成员吸回来。
- R2 匹配口径:与编辑器「自动添加」按钮完全一致——**模型名包含分组名**(双方 trim + 转小写后 `contains`,见 `web/src/components/modules/group/utils.ts` 的 `matchesGroupName`/`normalizeKey`)。命中的授权全部纳入(同渠道同模型多 Key 一并纳入,与正则吸纳同粒度)。
- R3 吸纳语义:**append-only**。已有成员一律不动(优先级、顺序、active_item_id 均不变);新成员按稳定排序追加到优先级末尾。不做任何删除。
- R4 适用范围:`member_regex = ''` 的分组,含 manual 与 failover 两种 mode。正则分组(`member_regex <> ''`)成员仍由正则整体替换定稿,手动吸纳不介入。
- R5 兜底:与正则兜底同一定时任务(5 分钟)串行追加一轮**全量**吸纳(不限渠道),幂等可重入。
- R6 后端实现,无前端改动、无 API 变更、无 schema 变更。

## Non-goals

- 不做「移除记忆」:手动删掉的匹配成员会在下次渠道变更/兜底时被重新吸纳(v1 同款行为,规避手段=改分组名或改用正则分组)。此为已知预期行为,写入 spec。
- 不恢复 v1 渠道侧 `auto_group` 字段及其 fuzzy/exact/regex 三模式。
- 不改编辑器「自动添加」按钮(口径本就一致)。

## Acceptance Criteria

- [x] AC1 新增渠道,其模型名包含某手动分组名 → 不做任何人工操作,该分组自动出现此渠道的对应成员;分组列表(缓存)、DB、UI 三处一致
- [x] AC1b 手动分组**创建**时,已存在的匹配渠道授权立即被吸纳,创建响应即带吸纳后的成员(API 实测);分组**改名**后立即按新名吸纳;未改名的成员编辑保存不触发吸纳(单测断言)
- [x] AC2 渠道更新新增了模型 → 新模型授权自动进匹配分组;分组内**既有成员的优先级与顺序不变**
- [x] AC3 正则分组成员始终由正则重算定稿,吸纳逻辑不碰它们(单测断言)
- [x] AC4 同一渠道重复触发吸纳幂等:不产生重复成员(单测断言)
- [x] AC5 手动删除某匹配成员后再触发渠道变更 → 成员回归(记录为预期行为,单测断言锁定语义)
- [x] AC6 兜底任务全量吸纳与事件吸纳共存不冲突(定时任务注册处串行调用)
- [x] AC7 单测覆盖上述语义;octopus-verify 全流程通过(容器内编译/后端测试/前端 lint+build/起容器/健康检查/UI 人审分组页)
