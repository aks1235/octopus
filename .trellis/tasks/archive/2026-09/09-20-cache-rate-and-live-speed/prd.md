# 缓存率显示 + 流式实时速度

## Goal

补齐两处信息(用户 2026-09-20 从上游 v0.13.5/0.13.6 挑出的增量):
1. **缓存率百分比**:日志卡片与详情把缓存 token 显示为 `数量 (百分比)`。
2. **流式实时速度**:请求进行中显示输出速度(字符/秒),完成后仍显示既有的精确 tok/s。

## Background

- 上游 v0.13.5 的「首字/实时速度/词元速度/缓存率」我们只取其两点(其余我们已有更准实现:实际 token 数推导,而非事件计数)。
- 上游的实时速度按**事件个数**计字符(`OutputChars++` 每个事件加 1),0.13.6 的 #398 正是在修这个(原为每事件 +2 导致虚高)。**我们不复用该口径**——按事件计数与真实输出量无稳定关系。
- 我们的流式循环本就每事件解析一次(相位分类 `streamEventPhase`;结束判定 `inspectStreamEvent`),速度的字符量应**搭车同一份解析**得到增量正文长度,避免新增解析开销。

## Requirements

- R1 **缓存率**:卡片与详情把缓存 token 显示为 `1,234 (87%)`;缓存率 = 缓存输入 token ÷ 输入 token(输入为 0 时不显示百分比);保留缓存写入量(若有)现有展示。
- R2 **实时速度(后端)**:`RequestState` 增加 `output_chars`(进行中已产出的正文**字符数**,由增量正文长度累加)与 `output_speed`(字符/秒,按发布时点计算);仅在流式进行中有值;按节流发布(复用/沿用既有节流节奏,避免每事件推送)。
- R3 **字符量口径**:按**解析出的增量正文文本长度**累加(OpenAI `delta.content` / Anthropic `text_delta` / Responses `output_text.delta`);reasoning(思考)增量是否计入——**不计入**,与"输出速度"语义一致(思考另由相位表达)。
- R4 **解析搭车**:实现上必须复用同一份事件解析同时得到(相位, 正文长度),不得为速度新增第三次解析;若既有两处解析(`inspectStreamEvent`/`streamEventPhase`)本可合并,允许合并但不得改变各自既有行为(结束判定与相位)。
- R5 **前端**:进行中(running/committed)卡片与详情显示实时速度(如 `⚡ 123 c/s`);完成后显示既有精确 `t/s`(由 usage + 耗时推导,不回归);i18n 三语。
- R6 非流式、manual、跨协议转换路径行为不变;速度字段不影响路由/统计/日志落库。

## Non-goals

- 不移植上游「按事件计数」的实现或其 #398 修复(我们不适用:该计数代码不在我们树里)。
- 不改既有 tok/s(完成后)的推导口径。
- 不做速度曲线/历史速度统计。

## Acceptance Criteria

- [ ] AC1 卡片与详情显示 `缓存 token (百分比)`;输入为 0 时不显示百分比;缓存写入展示不回归
- [ ] AC2 流式进行中显示实时字符速度,数值随输出增长而更新且量级合理(与真实增量正文长度一致,不虚高)
- [ ] AC3 完成后显示既有精确 tok/s,行为不回归
- [ ] AC4 每事件解析次数不增加(实现层证据:单次解析同时产出相位与字符量)
- [ ] AC5 i18n 三语;tsc/eslint/build 通过;octopus-verify 通过(UI 人审:长流式请求进行中速度滚动、完成后切 tok/s)
