# 正则分组支持拖拽渠道排序

## Goal

正则分组的成员集合仍由正则重算定稿(收紧正则可开除成员,语义不变),但**成员顺序支持人工干预**:在分组内拖拽成员改变渠道优先顺序,重算不再把顺序刷回固定排序。解决「手动调高的渠道优先级几分钟后被 5 分钟兜底任务覆盖」的问题(用户场景:`deepseek-v4-flash` 分组想把天翼云渠道排最前)。

## Background

- 正则分组(`member_regex <> ''`)成员由 `GroupRegexSync` 整体替换重算,排序固定为 (channel_id, model_name, key_name) 稳定升序(`internal/op/group.go` syncRegexGroupItems),顺序即 priority,路由 failover 按此遍历(`internal/relay/route.go` pickGroupItem)。
- 触发:渠道增/改 + 5 分钟兜底任务(`internal/task/init.go` TaskGroupRegexSync)。用户拖拽排序保存后,几分钟内被重算覆盖。
- 当时设计明确「正则组禁止手动编辑成员:手动增删会被重算覆盖,允许编辑是假象」(09-08-v2-feat-ops-obs design.md 权衡表)——本任务**不推翻**这条:成员集合仍禁手动增删,只开放**顺序**编辑。
- 现有拖拽组件:手动分组卡片 `web/src/components/modules/group/Card.tsx` 的 MemberList 已支持拖拽重排并整体提交 items。
- 顺序偏好是分组私有的:同一渠道在不同分组可排不同位置,故顺序表挂分组,不挂渠道。

## Requirements

- R1 顺序干预:正则分组成员列表开放拖拽排序(当前只读)。拖拽单位为**渠道块**:同渠道的成员在列表内连续,拖其中任一成员,该渠道全部成员整体移动,渠道内部仍按 (model_name, key_name) 自然序。
- R2 排序合成:重算(渠道增删改触发 + 5 分钟兜底 + 保存正则时)生成成员顺序 = **(人工渠道顺序, channel_id, model_name, key_name)**:人工排过的渠道按人工顺序在前段;未排过的渠道(含新吸纳)按原自然序追加在后段。人工顺序对未列出的渠道不生效。
- R3 持久化:人工渠道顺序按 (group_id, channel_id) 持久化,渠道删除后其顺序记录级联清理;渠道恢复(重新添加)不复活旧顺序。
- R4 语义边界:成员集合仍由正则定稿——UI 不开放单成员增删;拖拽只写顺序表,不写 group_items 的 priority(priority 仍由重算按 R2 合成顺序定稿,syncGroupItems 既有主键保留逻辑不变)。
- R5 手动分组不受影响:member_regex 为空的分组仍走手动吸纳 append-only 语义,本任务不改其行为。
- R6 兼容:无 schema 破坏性变更(新表/新列为增量);已有正则分组未设人工顺序时行为与现状完全一致(自然序)。
- R7 后端为主 + 前端交互;顺序读写走**独立轻量端点**(不并入 GroupUpdate,避免与「集合只读」语义混淆),无破坏性 API 变更。

## Non-goals

- 不做单成员级(跨渠道打散)排序——成员属于渠道块,打散会让渠道内顺序不稳定。
- 不改成员集合语义(不做正则组的成员手动增删、不做排除名单)。
- 不做渠道全局权重(顺序偏好不挂渠道实体)。
- 不动手动分组与手动吸纳行为。

## Acceptance Criteria

- [ ] AC1 正则分组内拖拽渠道块保存后,重算(渠道增改触发与 5 分钟兜底)不再覆盖人工顺序;路由按新顺序 failover
- [ ] AC2 新渠道命中正则吸纳后,其成员追加在人工排序渠道之后,按自然序;不破坏已有人工顺序
- [ ] AC3 拖拽单位是渠道块:同渠道成员整体移动,渠道内 (model, key) 顺序稳定
- [ ] AC4 渠道删除后顺序记录级联清理;重新添加同渠道(新主键)不复活旧顺序
- [ ] AC5 未设置人工顺序的正则分组,重算结果与现状完全一致(回归)
- [ ] AC6 手动分组行为零变化(回归)
- [ ] AC7 正则分组成员的手动增删在 UI 仍不可用(只读集合 + 可排序)
- [ ] AC8 octopus-verify 全流程通过(容器内编译/后端测试/前端 lint+build/起容器/健康检查/UI 人审:拖拽排序持久、兜底后顺序保持)
